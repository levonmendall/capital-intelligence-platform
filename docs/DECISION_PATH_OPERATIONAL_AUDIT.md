# Decision Path Operational Audit

## Purpose

This audit distinguishes architecture that merely exists in source code from logic that is actually invoked by the governed production paper decision path. The governing objective remains maximizing long-term compounded returns after costs. Nothing in this repair adds live-money authority, a seventh specialist, a second CIO, or a threshold bypass.

## Canonical production path

The active path is:

`Render supervisor`
→ `autonomous paper operator`
→ `scheduled / material-change context preparation`
→ `complete governed universe and point-in-time evidence`
→ `competitive opportunity qualification`
→ `Forward Decision Intelligence and governed forward evidence`
→ `candidate and joint risk`
→ `exactly six specialists`
→ `CIO-only decision`
→ `portfolio construction and reconciliation`
→ `paper authorization and implementation`
→ `canonical state / thesis / outcomes / historical learning`

The Streamlit and API surfaces remain read-only with respect to investment authority.

## Operational classification

### Active decision inputs

The production path invokes:

- complete-universe opportunity qualification and cash/current-holding alternatives;
- point-in-time market, macro, company/fundamental and valuation evidence;
- capital-flow and market-expectations intelligence;
- Forward Decision Intelligence;
- global bull-market / rotation radar and persistent opportunity sweep;
- candidate risk and joint-candidate intelligence;
- exactly six specialist analyses;
- robust candidate assessment, specialist reconciliation and opportunity-cost comparison;
- CIO synthesis and initial targeting;
- independent construction reconciliation.

### Active governance and controls

The path enforces:

- fail-closed evidence and certification boundaries;
- complete screening and candidate-evidence coverage;
- CIO-only portfolio authority;
- construction limits, turnover, drawdown and execution controls;
- exact-cycle construction / briefing / authorization matching;
- paper-only implementation;
- append-only portfolio and learning lineage.

### Active monitoring and learning

The runtime also invokes:

- material-change reassessment triggers;
- live thesis monitoring;
- after-close outcome review;
- governed historical-learning resolution;
- alerts and operating-state publication.

Historical samples can influence CIO confidence/size only when they satisfy the governed learning manifest and horizon/certification rules.

### Intentional non-authorities

These remain connected but cannot independently change the portfolio:

- public/educational headline collection;
- UI and API presentation;
- advanced-intelligence shadow observations;
- global radar nominations;
- exposure graph relationships;
- Forward Opportunity Discovery hypotheses.

## Integration gaps found and repaired

### Phase-5 forward engines

The strategic-business, governed market-trend, structural-theme, monetary-policy-transmission and currency-transmission engines existed and were unit-tested, but the production evidence builder did not instantiate them. A provider-neutral `ConfiguredForwardIntelligenceProvider` now activates these engines from explicit point-in-time dataset contracts and merges their output into the same `ForwardIntelligenceBundle` consumed by Forward Decision Intelligence and the six specialists.

Activation variable:

`CAPITAL_INTELLIGENCE_FORWARD_INTELLIGENCE_DATASET_BINDING`

Missing bindings remain unavailable rather than becoming synthetic signals.

### Rich exposure graph

The production radar previously constructed only metadata-derived relationships (asset class, economic exposure, country, currency, venue and underlying). The configured forward-intelligence provider can now load explicitly reviewed sector, industry, theme, issuer, product, supplier, customer, commodity or other supported exposure nodes/edges through the `exposure_graph` dataset. Every configured edge must declare `explicit_reviewed=true` and retains provider snapshot lineage.

### Value of Waiting

`ValueOfWaitingEngine` existed and Forward Decision Intelligence could consume its timing result, but the configured forward-research provider never materialized it. `event_expectations` may now carry the governed object form:

```json
{
  "expectations": [],
  "value_of_waiting": {
    "invest_now_expected_return": 0.0,
    "downside_if_unresolved": 0.0,
    "probability_uncertainty_resolves": 0.0,
    "expected_upside_lost_by_waiting": 0.0,
    "expected_post_event_entry_drag": 0.0,
    "transaction_cost_return": 0.0,
    "alternative_return_while_waiting": 0.0,
    "thesis_decay_return": 0.0,
    "evidence_identifiers": []
  }
}
```

Every timing input is explicit; the provider does not infer missing timing economics.

### Canonical event-to-market intelligence

Material public headlines already caused a fresh canonical reassessment, but headline content itself was intentionally non-authoritative. Separately, canonical decision-information and event-causal engines existed without a production bridge. The new governed event-forward bridge consumes only the configured licensed `DecisionInformationRecord` source, applies existing event-quality clustering, causal rules and market-confirmation gates, maps transmissions through the reviewed exposure graph, and enriches only candidates already admitted by the governed universe/evidence process.

Activation variable:

`CAPITAL_INTELLIGENCE_DECISION_INFORMATION_DATASET_BINDING`

The bridge cannot create a candidate or authorize capital.

## External activation boundary

A connected software path is not the same thing as live institutional evidence coverage. Repository code cannot create commercial subscriptions, exchange entitlements, credentials, licensing approvals, provider history or data that the deployment does not possess.

The source-controlled maximum-information manifest still contains disabled placeholders for several institutional sources. Therefore the correct operational claim is:

- the decision architecture is wired to consume the governed inputs when activated;
- missing institutional feeds remain explicit unavailable evidence;
- full all-market / maximum-information effectiveness requires the existing provider activation and certification process to be completed in deployment.

## Validation requirement

No repair is complete merely because an engine has a unit test. The merge gate must pass the repository's full deterministic release validation, including initialization, daily-plan validation, golden end-to-end/chaos, event-quality certification, institutional provider implementation readiness, all-markets internal readiness, universal paper availability, paper execution rehearsal, the complete pytest suite, browser tests and security review.
